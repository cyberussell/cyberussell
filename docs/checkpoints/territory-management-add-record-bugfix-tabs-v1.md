# Territory Management System — Add Record Validation Bug Fix + Territory Page Tabs — v1

**Date:** 2026-07-16
**Product:** Territory Management System (TMS)
**Feature:** Russell reported the admin's "Add a Contact Record" form always failed with a generic "Please fill in the required fields." error that also wiped every typed field, and asked (a) for the real required field to be surfaced, confirmed Plus Code should be required and Household members should default to 1 (matching the publisher form's already-established rule), and (b) for the Territory detail page's stacked layout (Details/Map, Sections & Blocks, Add Record, Records table all on one long page) to become tabbed, since Sections & Blocks renders every section and every block flat with no limit — a real scaling problem for a territory with e.g. 100 sections × 50 blocks.

## Files Modified
- `src/lib/territory-management-system/modules/records/schema.ts` — root-cause fix: `initialConductorName`/`initialNotes` (createRecordSchema) and `conductorName` (logVisitSchema) are conditionally rendered in their forms (only shown once a status that needs one is picked), so a native `<form action>` submits `null` for them via `FormData.get()` when hidden — `z.string().optional()` only accepts `undefined`, not `null`, so this silently failed validation on the common case (no initial status picked) even though every field was correctly filled in. New `optionalString()` helper normalizes `null` to `''` before validation. Also made `plusCode` required and `householdMembers` default to 1 on `createRecordSchema` (new `householdMembersDefaultOneField`, matching `assignment/schema.ts`'s existing `publisherHouseholdMembersField` pattern) — confirmed via `AskUserQuestion`, deliberately scoped to the create flow only, not `updateRecordSchema` (editing existing/legacy records still leaves a blank value unset).
- `src/app/territory-management-system/actions/records.ts` — `createRecordAction` now returns `parsed.error.issues[0]?.message` instead of a generic string, so whichever field actually failed (e.g. "Plus Code is required.") is what the admin sees.
- `src/lib/territory-management-system/hooks/useServerAction.ts` — now also returns the raw `state` object (in addition to `error`/`successMessage`), so a caller can react to *every* successful submission via reference identity rather than sentinel-string equality — needed because two consecutive successful saves both return the same `'SAVED'` string, which wouldn't register as a "change" to a `useEffect` keyed on the string alone.
- `src/components/territory-management-system/RecordForm.tsx` — converted from an uncontrolled native form (whose fields React 19 resets on every submit completion, success or failure) to fully controlled state. Fields now only clear after a confirmed `state.error === 'SAVED'`, never on a validation/server error. Plus Code label dropped "(optional)"; Household members kept "(optional)" since it still silently defaults rather than blocking submission.
- `src/components/territory-management-system/dashboard/territories/[territoryId]/page.tsx` — Territory Details form, Map upload, and the page header (CSV import/export, Delete Territory) stay above the fold; Sections & Blocks / Add a Contact Record / Contact Records are now three tabs via the new `TerritoryTabs` component, confirmed scope via `AskUserQuestion`.
- New `src/components/territory-management-system/TerritoryTabs.tsx` — same local-`useState` tab-switching pattern as `GroupLeaderTabs.tsx` (no URL state, no separate routes), minus that component's mobile fixed-bottom bar (this is an admin dashboard page already inside `DashboardSidebar`'s own navigation, not the publisher app shell). Only the active tab's content mounts.
- `src/components/territory-management-system/SectionBlockTree.tsx` — each section is now a collapsed-by-default accordion row (chevron + "Section X" + block count), expandable to reveal Add Block / block pills / Delete section — confirmed via `AskUserQuestion`. This is what actually fixes the scaling concern; tabbing the outer page alone wouldn't have, since all sections would still render at once inside the Sections & Blocks tab.

## Summary of Changes
- The bug's real mechanism (not what it looked like at first): the generic error message and field-wipe were two independent symptoms of the same underlying gap — a conditionally-rendered form field being absent from `FormData` submits as `null`, and Zod's `.optional()` rejects `null` (only `undefined`). This meant the admin's default path (leaving "Initial status" blank, the common case) *always* failed validation, and because the form was an uncontrolled native `<form action>`, React 19 resets all uncontrolled fields on every submit regardless of outcome — so a failed submission wiped everything the admin had just typed, with no indication of which field was actually the problem.
- Applied the required-Plus-Code / defaults-to-1-Household-members rule only to the create flow, matching what was already established for the publisher's own add-record form in an earlier session (explicitly scoped to publisher-only at the time) — Russell confirmed extending it to Admin's Add form for consistency.
- Live-verified the actual fix in the browser (not just code review) via a temporary scratch route (`src/app/scratch-territory-preview/page.tsx`, mock `TerritoryStructure` with real UUID-format ids, removed before commit): filled in Address + Resident name, left Plus Code blank, submitted — the browser's own HTML5 `required` attribute (now correctly wired since Plus Code is truly required) blocked it client-side with zero round-trip. Then explicitly disabled that `required` attribute via `javascript_tool` to force a real server round-trip anyway — confirmed the exact scenario: **"Plus Code is required."** appeared as the error, and "Purok 1, Rizal Street" (Address) stayed typed in the field, nothing wiped. Also live-verified `TerritoryTabs` with 8 mock sections × 6 blocks each: the Sections & Blocks tab shows 8 collapsed rows instead of 48 block pills at once; clicking a section expands it in place; tab switching between Sections & Blocks / Add a Contact Record / Contact Records works correctly.
- `npx tsc --noEmit` clean, `npx vitest run` 52/52 passing (existing suite untouched by this change — no existing tests target `records/schema.ts`), `npx next build` clean across all routes.
