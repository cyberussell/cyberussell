# Territory Management System — Per-Territory Reports Table + Household Distribution Map — v1

**Date:** 2026-07-16
**Product:** Territory Management System (TMS)
**Feature:** Russell asked the admin Reports page to add a per-territory table (Started Bible Study, Bible Study, Total Households, Total Records — light gray border, sorted by highest Total Households), asked whether Plus Codes could be plotted on a map to visualize household distribution, and asked whether deleting a section deletes its contact records.

## Answers to the two direct questions
- **Deleting a section deletes all its contact records: confirmed yes, at the database level.** `territory_blocks`, `territory_records` (both its `section_id` and `block_id` foreign keys), and `territory_record_visits` all have `ON DELETE CASCADE` back to `territory_sections` (`territory-management-system/migrations/001_init.sql`). The app code (`deleteSection` in `territory/queries.ts`) issues one `DELETE FROM territory_sections`; Postgres itself cascades the rest. No app-level "delete children first" step exists or is needed.
- **Google Maps vs. a free alternative — confirmed via `AskUserQuestion`:** Russell chose the free, no-signup option (OpenStreetMap tiles via Leaflet) over real Google Maps, since the latter would have required him to set up a Google Cloud project, enable billing, and hand over an API key before anything could work.

## Files Modified
- `src/lib/territory-management-system/modules/reports/queries.ts` — new `getTerritoryReportRows()` (per-territory Started Bible Study / Bible Study / Total Households / Total Records, sorted by Total Households descending) and `getApprovedRecordLocations()` (id/address/plusCode/territoryName for the map's pins).
- New `src/components/territory-management-system/TerritoryReportTable.tsx` — plain server-rendered `<table>` (not `DataTable.tsx`, deliberately — this list is small, always shown in full, and its highest-households-first order shouldn't be user-resortable), styled with actual `border-gray-200`/`border-gray-300` per Russell's explicit "light gray border" ask (the app's existing `DataTable`/`Card` convention uses a blue-tinted gray, which reads differently).
- New `src/components/territory-management-system/HouseholdDistributionMap.tsx` — client-only Leaflet map (`'use client'`, imports `leaflet/dist/leaflet.css`), one marker per approved record with a valid full Plus Code, OpenStreetMap tiles with required attribution, popup showing address + territory.
- `src/components/territory-management-system/ReportsView.tsx` — renders both new sections below the existing Visits stat grid; the map is loaded via `next/dynamic(..., { ssr: false })` since Leaflet touches `window`/`document` and can't run during server rendering.
- `src/app/territory-management-system/dashboard/reports/page.tsx` — fetches `territoryRows`/`recordLocations` alongside the existing daily/weekly/monthly stats, passes them down.
- `package.json` — new dependencies `leaflet`, `react-leaflet`, dev dependency `@types/leaflet` (leaflet ships no types of its own).

## Summary of Changes
- **Scope confirmed via `AskUserQuestion` before building** (3 questions): (1) map provider — free/no-signup Leaflet+OSM chosen over Google Maps; (2) Started Bible Study/Bible Study semantics — current record status (most-recent-ever visit, no date range) chosen, matching the existing `countActiveBibleStudies` "Bible Studies in the Area" stat's established definition rather than inventing a period-scoped variant; (3) Total Households scope — approved records only chosen (not all records, unlike Total Records which intentionally keeps the same all-records meaning `territory/queries.ts`'s existing `record_count` already uses, for consistency with that established precedent).
- **Plus Code → map pin, entirely client-side, no geocoding API**: the `open-location-code` package (already a dependency, previously only used for `.encode()` in `lib/plusCode.ts`'s "Use My Location" button) also exposes `.decode()`, which turns a full Plus Code straight into a `{latitudeCenter, longitudeCenter}` pair — confirmed this works with zero network calls before committing to the Leaflet approach. Short/local-form Plus Codes (e.g. "7FG8+4V" without a reference locality) are filtered out via `isFull()` since they can't be decoded standalone; only full codes produce pins.
- `getTerritoryReportRows` reuses the exact same "visits ordered newest-first, first time we see a record_id is its latest result" de-dup pattern already established by `getVisitResultCounts`/`countActiveBibleStudies` in this same file, just grouped by territory and split into the two distinct Bible-Study-related results instead of collapsed into one.
- `npx tsc --noEmit` clean, `npx vitest run` 52/52 passing (existing suite untouched), `npx next build` clean across all routes.
- **Live-verified in the browser** (not just code review) via a temporary scratch route (`src/app/scratch-reports-preview/page.tsx`, removed before commit) rendering both new components with mock data — 12 fake records with real full Plus Codes generated via the same `OpenLocationCode.encode()` around real Manila-area coordinates. Confirmed: the table renders with a visible light gray border and is pre-sorted highest-Total-Households-first (Maligaya 132 → Alunan Quezon 18 → two zero-household territories); the map renders real OpenStreetMap tiles with all 12 pins plotted in the expected geographic pattern, zoom controls work, and clicking a pin opens a popup showing the correct address + territory name.

## Known Issues
- Same standing limitation as every TMS session: the real Reports page (behind Supabase auth, real congregation data) wasn't click-tested end-to-end — verification used a mock-data scratch route exercising the exact same components.
- `getTerritoryReportRows`/`getApprovedRecordLocations` fetch all of a congregation's records (and, for the former, all matching visits) in one unfiltered query each, same pattern `territory/queries.ts`'s `listTerritories()` already uses — fine at current scale, would need pagination/aggregation-at-the-DB-level if a congregation's record count grows very large. Not treated as a blocker since it matches existing precedent rather than introducing a new pattern.
- The map plots every approved record with a full Plus Code congregation-wide in one view (not scoped per-territory or filterable) — matches the literal ask ("see the distribution of households") but Russell may want a per-territory toggle or color-coding by territory later if the congregation has many territories with overlapping geography.
