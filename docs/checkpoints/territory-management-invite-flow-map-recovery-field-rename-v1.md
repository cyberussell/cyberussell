## Root cause investigation (the real fix, not another guess)

**Invite link — confirmed via reading `@supabase/ssr` and `@supabase/auth-js`'s own installed source, not conjecture.** `@supabase/ssr@0.12.0`'s `createBrowserClient` hardcodes `flowType: 'pkce'` in its internal options object, placed *after* spreading any caller-supplied `auth` options — so there is no way to override it from the outside. Supabase's own `GoTrueAdminApi.js` doc comment states PKCE is categorically unsupported for `inviteUserByEmail()` ("the browser initiating the invite is often different from the browser accepting the invite"), meaning every Group Leader invite link is guaranteed to be an implicit-flow link (`#access_token=...&type=invite` in the hash). When a PKCE-forced client's `_initialize()` parses that URL, `GoTrueClient.js`'s own mismatch guard throws `AuthPKCEGrantCodeExchangeError` internally — caught, swallowed, and returned as `{session: null, error}` with **no auth event ever dispatched**. This is why the prior session's fix (listening for `SIGNED_IN` in addition to `PASSWORD_RECOVERY`, bumping the timeout to 8s) could never have worked: there was nothing pending to eventually fire, the failure was synchronous and silent. Confirmed this affects LMS's nearly-identical `accept-invite/page.tsx` too (same `createBrowserSupabase()` pattern, same missing override) — flagged but not fixed here, out of scope for this TMS-focused pass.

**Map — confirmed the exact character-count math, not assumed.** `openLocationCode.isFull()` rejects any short code by design; real Plus Codes typed manually at the door (like "5JJ6+F8", seen in this conversation's own screenshots) are short-form and were being silently dropped, which is why the map showed "No approved records with a Plus Code yet." even with real approved records on file. `recoverNearest()` exists and works today in the installed `open-location-code@1.0.3` package — only the hand-written `.d.ts` was missing its signature. For a 4-char-before-`+` short code, the algorithm needs the reference point within 0.5° (~55km) of the true location to recover correctly — comfortably true for any single congregation's own other records, which is why deriving the reference from already-decoded full codes in the same fetch (rather than a hardcoded city) is both correct and doesn't require a new stored "congregation location" field.

## Summary of Changes
- The `description`→"Barangay Name" required-everywhere change (confirmed via `AskUserQuestion`) means an existing territory saved before this change, with no description on file, will fail to save *any* other edit (name/status change included) until an admin fills in Barangay Name — this was Russell's explicit choice over grandfathering old rows in, so the UI now surfaces the specific "Barangay Name is required." message (not a generic one) when that happens.
- Only the four UI surfaces Russell explicitly named were touched (create form, edit form, Territories list table, Reports per-territory table) — the ~10 other places that display a territory's `name`/`description` (delete-confirm dialogs, CSV headers, the daily-assignment territory picker, publisher-facing map viewers, etc.) were deliberately left alone; they'll simply display whatever value ends up in those same underlying `name`/`description` columns, which is an acceptable, low-risk side effect of a pure relabeling change rather than a database rename.
- `npx tsc --noEmit` clean, `npx vitest run` 52/52 passing (existing suite untouched), `npx next build` clean across all routes.
