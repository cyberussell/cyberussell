1. **QR panel layout**: "Valid for today only — a new one is needed tomorrow." moved above the QR image (was below the public URL link), now smaller fine-print (`text-[11px]`). 2. **Real, confirmed whitespace bug found and fixed**: earlier in this session I wrongly concluded the "partnershipwere" typo (reported at the very start of this work) needed no fix because the source already had a literal space character before "were" on the same source line. Re-testing while verifying the QR panel changes proved this wrong — isolated browser tests (`textContent` inspection, not just visual inspection) confirmed the rendered DOM genuinely drops that space in this specific case, while a structurally similar paragraph elsewhere (`AssignmentForm.tsx`'s "insufficientForHeadcount" box) renders correctly. The exact trigger wasn't fully isolated (multiple controlled variations gave inconsistent results — length of trailing text seemed related but wasn't a clean rule), so rather than chase the precise compiler mechanism, fixed it the robust way: inserted an explicit `{' '}` JSX expression immediately after the pluralizing ternary, which can't be swallowed by whatever text-collapsing behavior caused this (confirmed live: renders "1 fewer partnership were created" correctly now). Swept the rest of TMS for the same ternary-then-long-multiline-text pattern (`AssignmentForm.tsx`'s two similar boxes, `OverflowAssignmentForm.tsx`'s summary) via live component rendering + `textContent` inspection — all confirmed already correctly spaced, no further fixes needed.
3. Also deleted a stray untracked duplicate file, `GroupLeaderTabs 2.tsx` (byte-identical to an old committed version of the real file, unreferenced by any import) that started failing `tsc` once the real file's props changed.

`tsc`/`vitest` (56/56)/`next build` all clean. Live-verified via two more temporary scratch routes (removed before finishing).

## Addendum — separate, more serious bug found and fixed via live reproduction (2026-07-19)
Russell reported (with fresh live screenshots) that a regular, non-overflow assignment on a territory with non-zero approved records still put **every** Ministry Partner into "Choose Your Search Area" instead of their real assigned-records list. Traced to `getPartnershipByToken()` (`assignment/queries.ts`) embedding `move_recommended_territory_id`/`move_recommended_section_id`/`move_recommended_block_id` (migration 033) and `correction_recommended_territory_id` (migration 034) — columns that were never applied to the live TMS Supabase project (flagged as pending in an earlier session's `working-on.md` entry but not acted on). With those columns missing, the query fails and `records` silently comes back `[]`, which trips `PublisherWorkspaceApp`'s `needsSearchScope = ... || workspace.records.length === 0` for every partnership regardless of `is_overflow`. **Not a code bug** — no source changes were needed. Fix was purely applying migrations `032_move_recommendation.sql`, `033_move_recommendation_location.sql`, and `034_correction_recommendation_territory.sql` to the live project, which Russell did via the Supabase SQL editor. Confirmed resolved.
