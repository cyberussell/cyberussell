# Territory Management System — Assignment Generation Capacity Cap — v2 (corrected rule)

**Date:** 2026-07-15
**Product:** Territory Management System (TMS)
**Feature:** v1 of this session got the rule backwards — it blocked generation when approved records *exceeded* partnership capacity, which Russell clarified is fine (extra records just carry over unused, the original design). After walking through two worked examples (50 records/10 publishers/group-2 → 5 partnerships, should succeed; 50 records/20 publishers/group-2 → 10 partnerships, should block), the real rule is: block when the *requested* partnership count exceeds what the approved records can actually support (`ceil(records / 6)`) — i.e. when some partnership would end up with zero records. Confirmed via `AskUserQuestion` before rebuilding: revert the v1 block entirely, use the ceil-based threshold, warning-text-only (no auto-suggested fix in the UI).

## Files Modified
- `src/lib/territory-management-system/modules/assignment/engine.ts` — removed v1's `records > partnershipCount * maxPerPartnership` block. Replaced the old `records < partnershipCount` "insufficient records" check with a single, strictly-more-precise check: `partnershipCount > Math.ceil(eligibleRecordIds.length / maxPerPartnership)`. This subsumes the old check (proof: if `records < partnershipCount` then `ceil(records/max) <= records < partnershipCount` always holds for `max >= 1`), so nothing was lost — it just also now catches the case the old check missed (e.g. 50 records into a 10-partnership sequential fill leaves partnerships 9-10 empty; old check passed since `50 >= 10`, new check correctly fails since `ceil(50/6)=9 < 10`).
- `src/components/territory-management-system/AssignmentForm.tsx` — reworked the preview box into two explicit bullets: (1) static "Each partnership can hold up to 6 approved records," (2) once territories are ticked, the approved-record total plus `ceil(total/6)` max supportable partnerships with a plain-English breakdown ("7 partnerships with 6 records and 1 partnership with 5 records"). Replaced v1's `exceedsCapacity` (records-too-high) logic with `insufficientForHeadcount` (`partnershipCount > recordsMaxPartnerships`, only evaluated when `eligibleTotal > 0` so it doesn't fire for the legitimate zero-record/brand-new-territory case) — same client + server double-enforcement pattern as before, button disabled when true.
- `src/lib/territory-management-system/modules/assignment/engine.test.ts` — reverted the test that had encoded v1's wrong behavior back to its original form (10 records/2 partnerships/max-4 succeeds with 2 unassigned). Removed v1's "too many records errors" test. Added tests for the new ceil-based block (9 records/3 partnerships fails, 9 records/2 partnerships succeeds at the exact ceiling) plus two regression tests transcribing Russell's own worked examples verbatim (50 records/10 partnerships fails, 50 records/5 partnerships succeeds with 20 unassigned).

## Summary of Changes
- The distribution algorithm itself (`calculateAssignment`'s sequential `.slice()` loop) is unchanged — partnership 1 still fills to max before partnership 2 starts, etc. What changed is *when the engine refuses to even try*: previously only "too few records for 1-each," now "too few records for every requested partnership to get anything," which is the actually-meaningful failure mode given how the fill algorithm works (a partnership past the `ceil(records/max)`-th one is guaranteed empty, not just under-filled).
- Live-verified in the browser preview (not just `tsc`/build) using a temporary scratch route (`src/app/scratch-assignment-preview/page.tsx`, removed before commit, not part of the diff) that rendered the real `AssignmentForm` component with mock territory data matching Russell's own screenshot (Centro II 0, Alunan Quezon 3, Casili 0, Estrada 0, Maligaya 47 approved). Confirmed all three states match exactly: (1) Maligaya ticked, 4 publishers/group 2 → bullet 2 reads "47 approved contact records available... enough for up to 8 partnerships (7 partnerships with 6 records and 1 partnership with 5 records)," no warning, button enabled; (2) publishers bumped to 20 (→10 partnerships) → red warning "Not enough approved records for 10 partnerships — only 8 of them can get records from the 47 available. Reduce publishers going out, increase group size, or have another Group Leader generate a separate assignment to cover the remaining publishers," button disabled; (3) publishers dropped to 10 (→5 partnerships) → warning clears, button re-enabled. This is a rare TMS pass with real in-browser confirmation of the actual behavior, not just code-level reasoning, since this specific form doesn't depend on Supabase/auth — only the `territories` prop, which was trivial to mock.
- No new migration needed — pure calculation logic, same as v1.
