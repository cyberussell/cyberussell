# Territory Management System — Map Upload Body-Size Fix + Password Token Premature-Expiry Fix — v1

**Date:** 2026-07-16
**Product:** Territory Management System (TMS)
**Feature:** Russell reported a production crash uploading a territory map, asked for a way to delete a Group Leader, and reported that an invited Group Leader can't change their password because the token "expires prematurely."

## Investigation findings (before any fix)
- **Map upload crash — root cause confirmed via real Vercel production logs** (`get_runtime_errors` MCP tool, not guesswork): `Error: Body exceeded 1 MB limit.` on `/territory-management-system/dashboard/territories/[territoryId]`, 3 occurrences, `statusCode: 413`. Next.js Server Actions default to a 1MB request body limit; the UI already advertised "JPG or PNG — up to 5MB" and `uploadTerritoryMapAction` already has a correct `MAP_MAX_BYTES` (5MB) check with a friendly error message — but any file over 1MB never reached that check at all, since the framework itself rejected the request before the Server Action ran, surfacing as a raw "Something went wrong" error boundary instead.
- **Group Leader deletion — already exists, no gap found.** `GroupLeadersManager.tsx` has Revoke / Restore / Delete per row, `deleteGroupLeaderAction` → `deleteGroupLeader()` correctly calls `supabase.auth.admin.deleteUser()` (service-role), which cascades to `profiles` via its `ON DELETE CASCADE` FK to `auth.users` — confirmed no separate `profiles` delete call is needed. `assignment_batches.created_by` is `ON DELETE SET NULL`, so deleting a Group Leader doesn't break or orphan their past batches. **The only reason Delete might not be visible/usable**: it's gated (both client- and server-side) to entries at least 6 months old — a recently-invited Group Leader's Delete button is disabled with a tooltip explaining why.
- **Password token premature expiry — real bug found and fixed, same class already hit and fixed once before in the LMS product.** `set-password/page.tsx` (shared by both password-reset and invite-acceptance links) waited for the `PASSWORD_RECOVERY` auth event only, with a hardcoded 4-second timeout before declaring the link "invalid or expired" — regardless of whether Supabase had actually rejected anything. `src/app/lms/staff/accept-invite/page.tsx` hit and fixed this exact issue previously: an invite-acceptance link can fire `SIGNED_IN` instead of `PASSWORD_RECOVERY` depending on the Supabase-js version, and 4 seconds is provably too short on a slow connection. That fix (listen for both events, bump to 8s) was never ported to TMS.

## Files Modified
- `next.config.ts` — added `experimental.serverActions.bodySizeLimit: "6mb"` (checked this project's own bundled Next.js 16.2.9 docs at `node_modules/next/dist/docs/.../serverActions.md` before writing, per this repo's standing instruction that this Next.js version can differ from training data — confirmed the config shape is unchanged from what the docs describe). This is a global setting (Next.js has no per-route body limit) — it raises the ceiling for every Server Action across all 7 products; the existing 5MB app-level `MAP_MAX_BYTES` check is still what actually enforces the real limit and will now be reachable.
- `src/app/territory-management-system/set-password/page.tsx` — `onAuthStateChange` now also accepts `SIGNED_IN` (not just `PASSWORD_RECOVERY`), and the "declare it expired" timeout is now 8000ms, not 4000ms — byte-for-byte the same fix already proven in `src/app/lms/staff/accept-invite/page.tsx`.
